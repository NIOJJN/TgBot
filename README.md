Я разобрался в причине и проверил её экспериментально. Вот что происходит.

## Причина: резка в режиме stream copy (`-c copy`)

`clipper.py:49-61` режет клип так:

```python
cmd = ytdlp_cmd() + [
    "-f", selector,
    "--download-sections", f"*{start:.2f}-{end:.2f}",
    "--merge-output-format", "mp4", "--remux-video", "mp4",
]
if precise:                                  # precise_cut = false по умолчанию!
    cmd += ["--force-keyframes-at-cuts"]
```

`yt-dlp` превращает `--download-sections` в такой вызов ffmpeg (`yt_dlp/downloader/external.py:453-456` и `513-514`):

```python
if start_time: args += ['-ss', str(start_time)]      # -ss ПЕРЕД -i
if end_time:   args += ['-t',  str(end_time - start_time)]
if not (start_time or end_time) or not params.get('force_keyframes_at_cuts'):
    args += ['-c', 'copy']                            # <- стрим-копи, без перекодирования
```

То есть: **`-ss` до `-i` (быстрый входящий seek) + `-c copy` (без перекодирования)**.

При `-c copy` ffmpeg физически не может начать выдачу с произвольного момента — он может стартовать только с **ключевого кадра**. Поэтому:

- **видео** откатывается назад к ближайшему ключевому кадру и начинает играть раньше запрошенного времени;
- **звук** при этом режется точно по запрошенной метке.

Видео уезжает вперёд относительно звука → **в начале клипа идёт картинка без звука**, и ровно на столько секунд, на сколько видео отстало от звука (это расстояние до предыдущего ключевого кадра).

## Чем это подтверждено

Я собрал синтетический источник (ключевые кадры строго каждые 6 c, писк в звуке каждую секунду), разложил его в HLS с **отдельными** плейлистами видео и звука — как раздаёт Twitch при `bv*+ba/b` — и прогнал через него точную команду yt-dlp:

| режим | pts первого кадра видео | pts первого пакета звука | немая голова |
|---|---|---|---|
| `-c copy` (как в `clipper.py`) | **-5.72** | **0.00** | **≈5.7 c без звука** |
| перекодирование (`--force-keyframes-at-cuts`) | 0.04 | -0.02 | нет |

Звуковая дорожка в режиме copy к тому же получалась короче запрошенной (8 c вместо 10 c). Это ровно ваш симптом.

Величина «немой головы» = расстояние от запрошенного начала назад до ключевого кадра, то есть **до длины GOP**. У Twitch ключевые кадры идут каждые ~2 c (это я замерил на реальном VOD: `360p` → кадры на 1.0 / 3.0 / 5.0 c), поэтому на низких качествах эффект мелкий. Но на `1080p60` / `best` (ваш дефолт `quality = "1080p60"`) и особенно если дорожки видео и звука имеют разные границы сегментов, разъезд легко доходит до нескольких секунд — у вас вышло 6.

## Решение

Включите точную резку — она уже есть в проекте:

```bat
run.bat run <vod_id> --precise-cut
```

или в `config.toml`:

```toml
[cut]
precise_cut = true     # точная резка по кадрам (медленнее, но ровнее)
```

Это добавляет `--force-keyframes-at-cuts`, yt-dlp тогда **перекодирует** секцию вместо копирования, и обе дорожки режутся ровно по запрошенным таймкодам. Цена — клипы делаются медленнее (перекодирование вместо копирования потоков).

## Что важно понимать

Дефолт `precise_cut = false` — это осознанный размен скорости на точность, а не баг в вашей установке: `README.md:608` описывает флаг как «точная резка по кадрам (медленнее, ровнее)». Побочные эффекты режима copy, которые вы могли не замечать:

- клип **длиннее** запрошенного интервала (лишние кадры в head);
- звуковая дорожка может быть **короче** видео (обрезается по `-t`);
- концовка клипа тоже неточная по той же причине.

Если перекодирование всех клипов слишком дорого, разумный компромисс — оставить `precise_cut = false`, но увеличить `clip_padding` (сейчас `6.0`), чтобы «немой» head всё равно попадал в запас до момента. Это не убирает рассинхрон внутри клипа, поэтому для публикации клипов я бы рекомендовал именно `--precise-cut`.
